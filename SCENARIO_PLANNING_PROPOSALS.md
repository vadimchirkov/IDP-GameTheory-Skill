# Scenario Planning для Flumina — проверенная программа P1/P2

> **Статус:** пересмотрено после проверки актуального кода и численного эксперимента.
>
> **Решение:** не переносить Scenario Planning Skill целиком. В P1 взять только
> `timeframe` и проверяемую многомерную `failure box` для Decision-адаптера. В P2
> рассматривать точечную provenance и усиление статистической устойчивости. R17,
> R18, MICMAC, MACTOR, morphology, CIB и SMIC сейчас не имеют необходимых входных
> данных и не должны попадать ни в универсальное ядро, ни в основной UX.

## 1. Что уже есть в Flumina

Flumina — decision-rehearsal система, а не полный foresight-процесс. Актуальный
поток уже разделяет ответственность:

- AI формулирует проверяемую модель;
- адаптер вычисляет результат детерминированно;
- paired-world Monte Carlo использует одинаковые миры для всех опций;
- Decision-адаптер требует вопрос, objective, 1–8 факторов и 2–5 опций;
- `researchSources` хранят URL, выдержку, назначение, поле и дату получения;
- assumptions/rationale отображаются отдельно от источников;
- текущий stress lens проверяет low/high режим одного фактора;
- C/D-адаптер отдельно поддерживает repeated games, conditioning, tournament,
  evolution и spatial dynamics.

Следовательно, утверждение, что Decision-анализ можно запустить без опций, неверно:
валидатор отклоняет модель, если опций меньше двух.

## 2. Что было проверено

### 2.1 Факт и суждение — полезно, но в основном уже реализовано

Формальная граница частично существует: публичные источники и assumptions хранятся
и показываются раздельно. Полная форма `signedBy / panel / commercialStake /
ontologicalStake / denseRegions / sparseRegions` не улучшает расчёт и создаёт
несоразмерную нагрузку для основного workflow.

Практический пробел уже: у конкретного параметра не всегда видно, взят он из
источника, сообщения пользователя или оценки модели. Это кандидат на P2, но не
причина вводить отдельный Stage и новый блок обязательных полей.

### 2.2 R17 сейчас неприменим

R17 требует два самостоятельных регистра: морфологические states и вероятностные
гипотезы. В Flumina такого разделения нет. `transitions.states` — состояния самой
симуляции с явным правилом перехода, а не гипотезы SMIC.

Из 12 проверенных example-файлов только один содержит transitions. Добавление
обязательного state↔hypothesis gate ради этого случая будет проверять не тот
контракт и заставит AI придумывать отсутствующий регистр.

**Решение:** отложить R17 до появления отдельного morphology/SMIC-адаптера.

### 2.3 R18 сейчас неприменим

R18 предполагает 20–30 исходных переменных, граф влияния, косвенные ранги и relay-
квадранты. Текущая Decision-модель принимает уже сокращённые 1–8 факторов и не
содержит графа переменных. Значения `rank`, `quadrant` и `relays` нельзя проверить —
их пришлось бы генерировать как очередные неподтверждённые суждения.

**Решение:** не добавлять R18. Вернуться к нему только при наличии реального
variable register и как минимум двух моделей, которым требуется MICMAC-подобная
редукция.

### 2.4 Purpose 2×2 избыточен, timeframe полезен

Для Decision-режима цель уже зафиксирована вопросом, objective и опциями. Для C/D
режима пользователь явно выбирает Strategic interaction. Дополнительный purpose-
select дублирует существующий выбор режима.

Временной масштаб действительно потерян. В имеющихся C/D-примерах диапазон `w`
соответствует примерно 2.5–50 ожидаемым раундам, но неизвестно, является раунд
днём, кварталом или переговорным циклом.

**Решение:** добавить одно необязательное поле `timeframe: string`, например
`"следующие 18 месяцев"` или `"10 квартальных переговоров"`. Не использовать
обязательный `horizonYear`: не каждая задача имеет календарный горизонт.

## 3. Численная проверка failure box

Проверка использовала простую axis-aligned box из одного или двух условий. Границы
искались на train-половине миров по квантилям 20/40/60/80%, затем без перенастройки
оценивались на holdout-половине. Это проверка полезности идеи, а не готовая полная
реализация PRIM.

Метрики:

- **baseline** — доля провалов во всех holdout-мирах;
- **density** — доля провалов внутри коробки;
- **coverage** — какую долю всех провалов покрывает коробка;
- **lift** — `density / baseline`.

Результаты пяти seed, по 6000 миров:

| Сценарий | Текущий stress | Baseline | Density | Coverage | Lift |
|---|---:|---:|---:|---:|---:|
| Один фактор | находит reversal | 25.1% | 100% | 80.2% | 3.99× |
| Два совместных фактора | reversal не найден | 5.5% | 57.6% | 85.6% | 10.43× |
| Обычный C/D example | отдельного box нет | 46.9% | 57.3% | 25.2% | 1.22× |

Интерпретация:

- однофакторная коробка не добавляет ценности: её уже объясняет stress lens;
- двухфакторная коробка находит реальный режим провала, который однофакторный
  stress пропускает;
- на обычной C/D-модели lift слабый, а выбранные границы меняются между seed;
  переносить box в C/D сейчас не следует.

При штатных 600 мирах двухфакторная закономерность сохраняла высокий lift, но
holdout-коробка содержала только 13–38 миров, а thresholds заметно менялись между
seed. Значит, результат нельзя показывать без quality gate и явного support.

## 4. Пересмотренный P1

P1 должен добавить один новый вычислительный результат и один недостающий элемент
контекста, не превращая Run в многостадийный workshop.

### P1.1 Optional timeframe

Добавить `timeframe?: string` в Decision и Strategic модели:

- AI формулирует его только когда временной масштаб известен или существенно влияет
  на модель;
- поле показывается рядом с вопросом/ситуацией;
- изменение timeframe делает прежний run stale;
- отсутствие timeframe не блокирует Run.

### P1.2 Validated failure box только для Decision

Начать внутри Decision-адаптера, не выносить преждевременно в универсальное ядро.

Минимальный контракт результата:

```ts
failureBox?: {
  rules: Array<{ factorId: string; side: "low" | "high"; threshold: number }>;
  alternativeOptionId: string;
  baseline: number;
  density: number;
  coverage: number;
  lift: number;
  support: number;
  failureCount: number;
}
```

Ограничения первой версии:

- максимум два условия;
- фиксированные квантильные candidates;
- детерминированный train/holdout split по индексу мира;
- failure на уровне мира означает, что другая опция даёт лучший oriented objective;
- после выбора box все опции повторно суммируются внутри holdout-cohort по тому же
  criterion, что и основная рекомендация;
- Pearson sensitivity и текущий stress lens остаются — box их не заменяет.

Показывать box только если одновременно выполнены условия:

- `support >= 50` holdout-миров;
- `failureCount >= 30`;
- `coverage >= 0.20`;
- `lift >= 1.5`;
- density выше baseline;
- коробка содержит два фактора или обнаруживает режим, который не объяснил текущий
  однофакторный stress;
- внутри holdout-cohort другая опция действительно обгоняет основную рекомендацию
  с тем же meaningful-margin правилом, которое используется текущим stress lens.

Если gate не пройден, UI не показывает слабую коробку. Вместо этого можно предложить
повторить анализ с большим числом миров.

### P1.3 UX

В отчёте нужен один компактный блок `Где рекомендация меняется`:

- условия человеческим языком;
- baseline → density;
- coverage и support;
- предупреждение, что коробка описывает модель, а не доказанную закономерность мира.

Не добавлять отдельную страницу, pipeline stages или обязательные вопросы.

### P1.4 Проверки и критерий готовности

Минимальные тесты:

1. одинаковый seed даёт одинаковую box;
2. однофакторный случай подавляется как дубль stress lens;
3. двухфакторный провал обнаруживается на holdout;
4. низкий support скрывает результат;
5. изменение timeframe делает run stale, но отсутствие поля остаётся валидным.

P1 считается полезным, если на наборе реальных Decision-сценариев box:

- проходит gate не за счёт in-sample переобучения;
- остаётся близкой по правилам при смене seed;
- хотя бы в одном случае находит условную рекомендацию, пропущенную stress lens;
- не показывается на сценариях без достаточного сигнала.

Реалистичная оценка P1: 3–5 дней, включая типы, расчёт, artifact persistence,
отчёт, UI и проверки. Оценка `1–2 дня` для прежнего Tier 1 была занижена.

## 5. Пересмотренный P2

P2 начинается только после проверки P1 на реальных задачах.

### P2.1 Provenance lite

Если пользователи действительно путают evidence и assumptions, добавить к полям
модели компактную основу оценки:

```ts
type Basis =
  | { kind: "source"; sourceIds: string[] }
  | { kind: "user" }
  | { kind: "model-assumption"; note: string };
```

Хранить mapping на уровне продуктового model-build artifact, а не Monte Carlo core.
Переиспользовать существующие `researchSources`, `fetchedAt`, `field` и agent metadata.
Не добавлять подпись, panel, commercial stake и ontological stake в основной UX.

### P2.2 Устойчивость box

Добавлять bootstrap/quasi-p только после базовой версии и только если он меняет
решение show/hide. До этого достаточно holdout, support, coverage и lift.

Возможные улучшения:

- проверка стабильности rules на нескольких deterministic folds;
- CTA увеличить число миров при недостаточном support;
- сравнение коробки между runs с разными seed;
- offline benchmark-статистика: как часто box проходит gate и находит вывод,
  пропущенный stress lens. Пользовательскую telemetry для этого вводить не нужно.

### P2.3 Обобщение только после второго потребителя

Не создавать общий `scenario-discovery` framework ради одного Decision-адаптера.
Выносить generic helper только когда второй адаптер покажет устойчивый lift и тот же
контракт failure predicate. Текущий C/D example этого не подтвердил.

### Что не входит в P2

- Purpose 2×2 select;
- R13 generator из `registers.json`;
- feasibility register;
- R17 и R18;
- MICMAC, MACTOR, morphology, CIB, SMIC;
- Python subprocess в основном Run workflow.

Эти возможности могут появиться только как отдельный Scenario Planning adapter с
собственным UX, если возникнет подтверждённый enterprise use case.

## 6. Итоговое решение

Полезная часть исходного предложения существенно меньше заявленных 35%:

1. **делать в P1:** optional timeframe + validated two-factor failure box;
2. **проверить в P2:** provenance lite и статистическую устойчивость box;
3. **не делать сейчас:** R17, R18, purpose matrix и полный foresight pipeline;
4. **не менять:** универсальное Monte Carlo/topology ядро.

Исходные `scenario-planning/SKILL.md`, `pipeline.md`, `authoring-prompts.md` и
`algorithms.md`, на которые ссылалась первая версия документа, в workspace не
найдены. Поэтому их внутренние примеры `220/729`, `0/10` и claims о loop-back не
считаются независимо воспроизведёнными. Числа выше получены на актуальном коде
Flumina и проверены на holdout по нескольким seed.
